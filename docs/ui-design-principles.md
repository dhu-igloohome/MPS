# UI 设计原则（Igloo Foretracker / MPS）

> 本文件记录 David 定下的界面原则。**写新页面、改旧页面时先看这里。**
> 与 `ui-control-width-checklist.md`（控件宽度）互补：那份管"宽多少"，这份管"该不该有这个东西"。

---

## 原则 1：避免不必要的辅助标签与说明

界面上每多一段说明文字、一个小标签、一个提示条，用户就多读一样东西，也多一样要维护的东西。**默认不加；只有去掉之后用户会做错事，才加。**

**不要加（反面例子，前几项在本仓库里都出现过）：**

| 类型 | 例子 | 为什么多余 |
|---|---|---|
| 重复的标题 | 页面标题 "Order fulfillments"，下面面板标题又是 "Order fulfillments" | 同一句话说了两遍 |
| 复述控件的说明 | 按钮"添加行"旁再写"保存前可继续添加 SKU 行" | 按钮自己就在说 |
| 页面级"关于本页"折叠段落 | `AppShell` 的 `description`、"About this module" | 没人点开；需要解释的页面，该改页面本身 |
| 常驻的使用说明 / 口径说明块 | Forecast 全景的 "Three anchors / 三条读数依据"、"Notes" | 把解释当内容摆着，挤占数据 |
| 给每个字段配一行小字 | 表单项下面再加灰色 helper text | 字段名 + 占位符 + 默认值已经够了 |
| 为已有信息再造标签 | 区域旁再写"区域："、数字旁再写"数量："且表头已有 | 位置已经说明了它是什么 |
| 只为解释系统而存在的提示 | "已隐藏 N 条，点此显示" 这类需要先读懂系统才有意义的话 | 说明设计本身不直观，应改设计 |

**可以保留（例外，必须同时满足"不写会导致错误决策或错误数据"）：**

- 一个**指标的口径**，且口径不同会得出不同结论（例：漏斗里"发货 = 订单履约所有货运行的 SO 数量，含备货中"）。放进 `title` 悬停或一行小字，不要整段。
- **不可逆或有副作用的操作**的确认与后果（删除、批量删除、会写入生产数据的导入）。
- **可访问性文字**：`aria-label`、`title`、屏幕阅读器专用文字不算"多余标签"，**不要删**。
- 出错时的**具体错误信息**（哪一行、为什么）。

**怎么判断：** 把这段文字遮住，一个第一次来的同事凭布局、字段名、默认值能不能做对？能 → 删；不能 → 先试着改布局，改不了才留一行。

## 原则 2：让布局本身发挥解释作用

用**位置、分组、顺序、对齐、大小、颜色和默认值**说话，不要用字说话。

**手段（按优先用的顺序）：**

1. **分组与邻近**：相关的东西靠在一起、用空白或细线隔开，一眼知道谁和谁是一组（例：目的国与 Incoterm 合并在一格，数量与 BTS/BTO 标签叠在一起）。
2. **顺序即流程**：从左到右、从上到下就是操作顺序；主要的放最前（例：视图标签 All / In progress / Needs attention，最常用的 All 排第一且默认选中）。
3. **默认值替用户做选择**：能预填就预填，用户只改例外（例：月份默认当前月 +4，目的国、Incoterm 按区域预填）。**默认值是说明书。**
4. **一个视觉层级只表达一件事**：橙色实心只给"保存"；颜色标签只表达状态（Ops action 的绿/蓝/琥珀/紫）。
5. **空状态本身指路**：没有数据时，空状态里放"下一步该做什么"的那一个按钮，不放一段解释。
6. **图标 + `title` 代替文字按钮**（次要操作）：编辑、删除用行末图标，悬停才显示。

**反过来：** 如果一个页面需要一大段文字才能让人看懂，那是布局出了问题，**改布局，不要补文字。**

---

## 优先级

**精力放在 UI 和交互上**：控件怎么摆、点击几次完成、默认值是否合理、反馈是否及时。
不为"让文档好看"或"让页面显得完整"加内容；不为单个使用者加专属功能或说明（MPS 约 25 人使用，每个人都是普通使用者）。

---

## 修改旧页面时

- 一次只清理自己正在改的页面，**不做全站一次性大扫除**（风险大、难验证）。
- 删文字前先看它是不是上面"例外"里的一种。
- 中英文两套文案要一起删（`language === "en" ? … : …`），别只删一边。
- 删完在页面上过一遍：同事不看任何说明，能不能做完这个页面的主要任务。
